# 開発ルール

このドキュメントでは、MikanSNSを開発する上での基本的なルールを説明します。

---

## 開発技術

大まかな技術構成はREADMEにも載せました。  
実際の開発での各技術の立ち位置は以下の通り

- Next.js                    ：一番の大枠になるワークフレーム。

  - React                    ：Nextに内包されているUI（画面構成）構築のためのライブラリ。

  - TypaScript(言語)         ：Nextアプリを記述するための言語。
    - .tsx                   ：TypeSctiptと、HTMLのようなUI記述の構文を組み合わせた主にReact特有のファイル形式
    - .ts                    ：純粋なTypeScript。UIを生成しない処理に使う。

  - CSS(言語)                ：UIにデザインを施すための言語。色を変えたり大きさを変えたりアニメーションを付けたり。
    - .module.css            ：部品ごとにCSSを分割することのできる魔法の形式。

- Supabase                   ：ログイン認証をしたり、データを管理したりする外部サービス。こちらの整備は管理者がします。
  - Supabase SDK             ：TypeScript上から関数のようにSupabaseとの遣り取りをするための開発キット。こちらは使うかも。

ということで、*扱う言語はTypeScriptとCSS、作るものはNext.jsアプリケーション*とおぼえておきましょう。

---

## 開発の流れ

このプロジェクトでは*機能ごとに開発を進めていく*スタンスを取っている。  
(Feature-based Architectureについては[こちら](/docs/architecture.md))  
これはファイル構成だけでなく、仕事分担に関しても同様です。機能を一つずつ整備していくことで全体を作っていきます。  

また、*タスクの管理はGitHub Issue*で行います。都度チェックするようにしましょう。  

実際の流れとしては、  

GitHub上で*Issueを確認*  
↓  
Issueの*Assigneeを自分に設定*  
↓  
*Branchを切って*開発を開始  
↓  
諸々の機能を実装  
↓  
*Pull Requestを出して評価*し、通ったらmainブランチに統合  

という流れ。  
(Gitの仕組みや使い方がわからない場合は[こちら](/docs/git.md))

なお、バグや修正事項を見つけた場合には*積極的にIssueを立てるように*しましょう。(あるいは管理者に連絡するか)

## コーディングルール

細かいルールはESLintやPrettierにおまかせしたいところ
（lint全然確認してないせいで今めちゃくちゃですごめんなさい）

開発中は以下を意識しましょう

- 既存のコードの書き方に合わせる
- ある機能だけで使うものはfeatures内に置く
- 分からない場合は相談する

---

## ブランチ命名

ブランチの命名規則は以下の例に倣いましょう

feature/login-form
feature/profile-page

fix/navbar-overflow
fix/post-submit

docs/readme

作業が終わってPull Requestがマージされたら、ローカル・リモートともにブランチを削除してください。

---

## コミット

コミットはできるだけ小さな単位で行いましょう！  
コミットメッセージには、UPDATE/ ADD/ FIX/ REFACTORなど変更の種類を書いてくれるとありがたいです。
(タイトルと内容を改行挟んで書いてくれるとなおよし)

例： UPDATE: 投稿取得関数を変更 / 投稿取得数に上限数を設定した

---

## Pull Request

Pull Requestを出す前にエラーが出ないことを確認しましょう。
その際変更点を完結に書いてくれると嬉しいです。

---

## Issueについて

Issueは担当作業だけでなく、

- バグを見つけた
- 改善案を思いついた
- 実装したい機能がある

という場合も自由に作成してください。

「すぐ実装するかどうか」は別として、アイデアを残しておくことが大切です。
